## Agent journeys

Journeys whose actor is an agent.

### J1 Register and log in (rank 1, critical; depends on nothing)

Actor: agent (any identity). An agent registers its public key (open registration on loopback/unix, or with an enrollment token elsewhere), then exchanges a signed client assertion for a short-lived bearer used by every other call.

1. register (POST /v1/auth/register): body identity, public_key_jwk, enrollment_token only where registration is `enrollment`; 201. Registration is open on loopback or unix listeners, enrollment elsewhere (CLAUDE.md).
2. token (POST /v1/auth/token): form-encoded private_key_jwt client assertion (iss and sub are the identity, aud the issuer URL); 200 bearer.

### J2 Send and receive with ack (rank 2, critical; depends on J1)

Actor: agent. An agent opens a session, sends a message to a channel (general exists by default), receives it as another identity's session, acknowledges the batch token on its next receive, and closes the session.

1. openSession; sendMessage to `general` (a second identity sends so the first has something to receive, as in the e2e sequence); receive (batch plus batch token); receive again with ack set to that token (ack_ignored false); optional peek; closeSession.

### J3 Memories: create, read, edit, revise, delete (rank 3, high; depends on J1)

Actor: agent. An agent creates a channel of kind memory, sends a message to it (which is the first revision, result carries memory_id), reads it, edits it with if_revision, lists revisions, then deletes it.

1. createChannel kind=memory; sendMessage (result has memory_id, revision, replaced); getMemory; editMemory with if_revision (a stale value is `conflict`); listMemoryRevisions; deleteMemory. Memory channels are never delivered to agents on receive (CLAUDE.md, decision 20).

### J4 Task list: claim and complete (rank 4, high; depends on J1)

Actor: agent. An agent creates a channel of kind tasks, creates a task, claims it, updates it to done; a second path releases a claimed task instead.

1. createChannel kind=tasks; createTask; listTasks; claimTask; updateTask to done; getTask. Alternate: claimTask then releaseTask. Task operations need write permission on the list.

### J11 Task list: create and maintain (rank 5, high; depends on J1)

Actor: agent. An agent creates a channel of kind tasks and builds a plan in it, then keeps the plan current.

1. createChannel kind=tasks.
2. createTask for a top-level task; createTask with parent for two subtasks, the second placed with before or after the first; createTask with add_blocked_by naming another task.
3. listTasks (tree order); updateTask to edit subject and description, set owner, move a task with before or after, remove_blocked_by, and set status; getTask shows each change.
4. listTasks filtered by status and by owner. Task operations need write permission on the list.

### J6 Search and history (rank 7, medium; depends on J2)

Actor: agent. An agent reads a channel's history (optionally a thread) and searches across the channels it may read.

1. sendMessage (seed, from J2); history; search.

### J7 Agent status board (rank 8, medium; depends on J2)

Actor: agent. An agent sets its one-line status in its session, lists every identity's status and reads one identity's status history.

1. openSession; setAgentStatus (server validates the tag); listAgentStatuses; agentStatusHistory for the identity.

## Human user journeys

Journeys whose actor is a person signed in through a corporate provider (the TUI on a server profile). J12 to J14 were approved by Eric 2026-11-19; no Arazzo workflow covers them yet.

### J12 Human sign-in (rank 12, high; depends on nothing)

Actor: human. Drafted by Claude, approved by Eric 2026-11-19. An operator admits the person on the host; the person signs in at the corporate provider and the client exchanges the provider's access token for a short-lived human bearer. The first sign-in creates the human's identity. A human never registers a key.

1. Precondition (host, no HTTP operation): an `issuers` entry is configured and a `users` entry matches the person (`server admin users add -issuer corp -email V`, `-group V` or `-subject V`, or `create-human EMAIL`). A person who matches no `users` entry is refused at the exchange and no identity is created (docs/ops/admin-bootstrap.md:98).
2. The person signs in at the provider (authorization code flow with PKCE, outside this API; `agentmesh tui` and `agentmesh login -human` run it).
3. token (POST /v1/auth/token): form-encoded grant_type urn:ietf:params:oauth:grant-type:token-exchange, subject_token the provider's access token, subject_token_type urn:ietf:params:oauth:token-type:access_token (an ID token type is refused), audience optional (the server's issuer URL); 200 human bearer, lifetime the issuer's human lifetime (default 900 seconds). A second exchange answers a bearer for the same identity.
4. register under the human's name: 403 (a human identity cannot register).
5. Open for a workflow: the subject token must come from a fake provider (internal/oidctest), as in internal/conformance/bus/federated_test.go.

### J13 Follow the bus as a human (rank 13, medium; depends on J12)

Actor: human. Drafted by Claude, approved by Eric 2026-11-19. A signed-in human watches agents work: channels, history, new messages, memories and the agent status board.

1. openSession with a hint (the TUI uses the host's short name, so the session shows as `eric/macmini`); listChannels.
2. history on a channel; receive, then ack the batch on the next receive. A human receives memory channels; the Deliver rule withholds them from agents only.
3. getMemory; listMemoryRevisions.
4. listAgentStatuses: agents whose tag is `needs-human` or `blocked` make the TUI's attention count.
5. closeSession.

### J14 Answer an agent as a human (rank 14, medium; depends on J2 and J12)

Actor: human, with an agent. Drafted by Claude, approved by Eric 2026-11-19. An agent asks for help; the human answers in the thread; the agent acts on the answer as an instruction from its operator.

1. (agent) setAgentStatus with tag `needs-human` and a problem; sendMessage with the question.
2. (human) listAgentStatuses shows the agent; history on the channel finds the question; sendMessage with reply_to set to the question's seq.
3. (agent) receive: the reply's sender_kind is `human`, which agents treat as an instruction from their operator (internal/mcpserver/server.go:142).
4. (agent) setAgentStatus back to working.

## Administrator journeys

Journeys whose actor administers the server (the administrator flag) or a channel (admin on its ACL).

### J5 Admin bootstrap (API half) (rank 6, high; depends on J1)

Actor: administrator. Host: operator runs enrollment create and admins add (no HTTP operation). API: the administrator registers with the token, exchanges it, creates a scope, a scoped agent identity (returns a one-time enrollment token), a human identity by email, lists signing keys and reads admin status.

1. Host commands with NO HTTP operation, not a gap in the API: `agentmesh server admin ... enrollment create -identity NAME` and `admins add -identity NAME` (admin-bootstrap.md:45-63). Arazzo should take the token and the administrator identity as workflow inputs.
2. register (with the enrollment token); token; createScope; createAgentIdentity (with scope; returns a one-time enrollment_token); createIdentityByEmail; listSigningKeys; adminStatus.

### J8 Channel access management (rank 9, medium; depends on J1)

Actor: channel administrator. A creator makes a channel with an ACL, reads and replaces the ACL, subscribes another identity, and renames or deletes the channel.

1. createChannel with acl; getACL; setACL; subscribe; listChannels; renameChannel; unsubscribe; deleteChannel.

### J9 Slack bridge for a scoped channel (rank 10, low; depends on J5)

Actor: administrator. An administrator bridges a channel of an open scope to a private Slack channel, lists and gets bridges, then removes one. A server without Slack tokens answers 503 unavailable (not retryable, text 'the Slack bridge is not configured') to every bridges call.

1. Precondition: an open scope and a channel in it with a named-only ACL (createScope, createChannel with scope and ACL). Without Slack token files every call below answers 503 `unavailable`, not retryable, text `the Slack bridge is not configured`. The assertion is in internal/server/bridges_test.go:131 and internal/cli/bridges_test.go:91 (the e2e package does NOT exercise bridges; the brief's claim that it does was not found). A workflow against a server without Slack should expect 503.
2. createBridge; listBridges; getBridge; removeBridge (204).

### J10 Signing key rotation (rank 11, low; depends on J1)

Actor: administrator. An administrator lists the server's signing leaves, forces a renewal (a renewal always revokes every other unexpired leaf under the installation's intermediate key), exchanges a fresh client assertion for a new bearer, and lists again to see the new current leaf.

1. listSigningKeys (this process's current leaf first); rotateSigningKey (a forced renewal: the answer names the new current leaf and each revoked leaf with its `human_messages` count, always 0 until spec 2; the bearers a revoked leaf signed stop verifying, so the administrator exchanges a new client assertion for a bearer); token; listSigningKeys with the new bearer. The server needs the trust settings, with the intermediate key in a file or a key service; local mode answers 503 `unavailable`, not retryable.

## Summary
Fourteen candidates in three groups (Eric 2026-11-19): agents (J1 to J4, J6, J7, J11), human users (J12 to J14) and administrators (J5, J8 to J10). The required journeys are J1 to J5, J9 and J11 (J11 added by Eric 2026-11-07; J6 to J8 and J10 are extras). IDs and ranks are unchanged by the grouping, because api/arazzo.yaml and the tests name the journeys by ID. Documentation is rich, so ranking follows README and docs/ops. Least certain: J9 (bridges: the brief says the e2e test asserts the 503, but only unit tests in internal/server and internal/cli do), J7 (agent status: spec-backed but secondary), J8 (channel ACL management: criticality lowered to medium) and J3 (the memory id and revision flow through sendMessage was read from the schema only, not traced in the handler). Surface coverage is 40 of 57 operations.
