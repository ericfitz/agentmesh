# ADR 0019: Certificate hierarchy and signed messages

Status: Accepted (Eric, human-made): Decisions 1 to 21 of 2026-11-11 and Decisions 22 to 42 of 2026-11-12 below. Decision 40 reduces spec 2 to human messages and supersedes Decisions 8, 14, 17, 20, 21 and 29; their entries stay in the list, marked. The plan rulings are not Eric's decisions; he may overrule any of them. Open question 29 is settled (Decision 36), but the number it needs from IANA is pending, and spec 1 does not ship until it arrives. Four open questions remain, all in spec 2 and all about how to read Decision 40 (Open questions 55 to 58). Eric approved both specs on 2026-11-11; the spec text that folds in Decisions 22 to 42, the rewrite of spec 2 included, has not been approved by him yet. Designed, not built.

The design is in two specs: `docs/superpowers/specs/2026-11-11-certificate-hierarchy-design.md` (spec 1, the hierarchy, shippable alone) and `docs/superpowers/specs/2026-11-11-signed-messages-design.md` (spec 2, signed human messages, which depends on spec 1).

Partly supersedes ADR 0012 and the signing keys addendum of ADR 0004; see "What this supersedes".

## Context

The server signs bearers with a key from the `signing_keys` table, and trusts the public key of every row of that table (`internal/core/signingkeys/keyring.go:39-63`). By default the private key is in the row as well (`internal/store/signing.go:17-19`). A message's `sender_kind` is copied from the sender's identity row (`internal/core/messaging/send.go:144`), and agents are told to treat a `human` message as an instruction from their operator (`internal/mcpserver/server.go:142`). So whoever can write the database can forge bearers and can write messages that steer every agent (threat 2 and SD1 of `docs/security/threat-model-server.md`).

Two earlier answers were recorded in ADR 0012 and are not being built: the key set trust addendum (2026-11-09) and the server key file design (2026-11-10), which Eric abandoned on 2026-11-11. In abandoning it he accepted that write access to the database is the same privilege as administering the application, and named two subjects for the replacement: key storage and rotation, and provenance for human-initiated messages. This ADR records his design for both.

Eric's outline of 2026-11-11, condensed: a root CA with a private key, which can be anything and is not used for TLS, with the root certificate pinned in the server's configuration and given to clients at registration. Each installation is an intermediate CA under the root: a "generate" step makes a private key (a file or a key service) and a certificate signing request, and the administrator returns the certificate. The signing key is a private key with a certificate the intermediate issued. CRLs for revocation, delivered in band. A validity window with two active certificates at all times, renewal at half the window, and failed renewals retried more often toward the end. A server API forces immediate renewal with revocation of the previous certificate. No signing of data in the database: the server signs the message before the insert and stores the signed blob, with fields still extracted into columns for filtering and search. The client validates before acting; an invalid signature is an error and the client does not act. No keys in the database and no dependence on database integrity: assurance moves to the server before the insert and to the client after receipt and before use.

Two points of the outline were later changed by Eric himself: clients get the root from the discover document, not at registration (Decision 19), and clients verify every message, not only human ones (Decision 14). On 2026-11-12 he went back on the second: only human messages are signed and verified (Decision 40).

## Decisions (Eric, 2026-11-11, human-made)

Decisions 1 to 15 were made in the design session. Decisions 16 to 20 are his rulings, the same day, on open questions the first draft of the specs (commit `d3f5b56`) raised. Decision 21 is his ruling on Open question 28, which the second draft raised.

1. **Human assertion.** The server signs sender kind `human` only when the request's bearer carries a human claim, and only the OIDC browser sign-in exchange sets that claim. The identity row's kind is never consulted for it. **Wording corrected for the Slack path by Decision 31.**
2. **Slack-origin humans.** The signed blob carries `origin=slack` with the Slack user id, the email Slack reported and the Slack timestamp. `origin=api` carries the sign-in claim (the signed-in email). Clients treat both as human and can show which.
3. **Replay.** The client keeps, outside the database (the session state file, `internal/sessionstate`), the highest acknowledged sequence number per channel; a delivery at or below it is marked `replayed`. A human message whose signed origin time (the Slack timestamp for Slack origin, else the server timestamp) is older than a bound at delivery is marked `stale`. The bound is a client setting, default 24 hours. Both marks mean "history, not an instruction". **Extended by Decision 24** (the origin time is bounded; a message dated ahead of the client's clock is marked too). **Left without a mechanism by Decision 40**: that decision's two drops (a human message from before the session opened, and a repeat) do what the two marks were for, and the specs no longer carry the marks or the setting. Eric did not name this decision when he made Decision 40; spec 2, Open question 58 asks him to confirm.
4. **Leaf key.** In memory, one per server process, generated at start, never written anywhere; the intermediate issues its certificate. The same leaf signs bearers and messages. One intermediate per installation, shared by replicas.
5. **Old messages.** A message verifies when its signed server timestamp is inside the signing leaf's validity window, the chain reaches the pinned root, and neither the leaf nor the intermediate is on a CRL. Expiry alone never invalidates history. Revocation invalidates everything that certificate signed, whenever it was signed. **Extended by Decisions 26 and 27** (an intermediate is revoked by key; a revocation once seen stays). Since Decision 40 the messages it speaks of are human messages; no other message is signed.
6. **CRL freshness: broadcast only.** No pull endpoint with next-update enforcement and no fail-closed state for a stale CRL. A database writer who suppresses or rolls back the stored CRL can hide a revocation from clients that have not seen it; this is an accepted risk, bounded by the leaf's lifetime. **The bound is restated by Decision 24**, and again for Decision 40 in accepted risk 8; Decision 27 limits what a rollback undoes.
7. **Two configurations only.** Local mode (the in-process core over the user's SQLite file): no CA, no signatures, clients verify nothing. Server mode: a pinned root and an intermediate are required to start; there is no unsigned server. Development and tests use the shipped root tool.
8. **Coverage.** Every message written through `core.Append` is signed: chat, memory revisions, task documents, notices. Agent statuses stay unsigned; clients are told a status is display text, never an instruction; the threat model lists "a database writer can plant status text". **Superseded by Decision 40**: only a message appended with sender kind human is signed.
9. **Root tooling.** agentmesh ships a small root CA tool, with the root key in a file the administrator keeps offline. It serves development, test fixtures and small production installations. It is standard X.509, so an outside CA can replace it; the documents state the certificate profile an outside CA must issue.
10. **Intermediate key storage.** A PEM file (mode 0600, named by a setting) or one of the four existing key service backends of `internal/keyprovider` (`awskms`, `gcpkms`, `azurekms`, `hashivault`), which sign in place. The in-database provider is deleted. No backend that fetches a key from a secrets manager.
11. **Envelope.** Each message is a compact JWS (EdDSA or ES256) whose payload is the message as JSON and whose header names the leaf by certificate thumbprint. Leaf certificates are stored once each in a public table; every response that carries messages also carries the certificates they reference. Clients act only on fields parsed from the verified payload. **Narrowed by Decision 40**: only a human message has an envelope, and the payload is the one that decision names.
12. **Broadcast.** No message row announces a CRL. Session open and every receive result carry the current CRL number; a client that reports an older number gets the CRLs and the chain in the same response. A forced renewal also rings the wake doorbell for every waiting session. Clients refuse a CRL with a lower number than the one they hold. **Changed by Decision 27**: a client whose number differs gets the bundle, not only one whose number is older.
13. **Two specs and one ADR.** The hierarchy first, shippable alone; then signed messages on top.
14. **Clients verify every message** in server mode, not only human ones. This overrides "optional for agent messages" in the outline; Eric accepted it. **Superseded by Decision 40**: clients verify the messages that claim to be from a human, and no others.
15. **Database write still equals application administrator** for what the server reads to decide: ACLs, the administrator flag, identity rows other than the human claim. Replicas and restores are included.
16. **A forced renewal invalidates the revoked leaves' history; accepted.** (First draft's Open question 5, option A.) Everything the revoked leaves signed stops verifying, memories and tasks included. The command reports, for each revoked leaf, the counts of messages, memory revisions and task documents it had signed. **Changed by Decision 40**: a forced renewal invalidates only the human messages the revoked leaves signed. No memory or task becomes uneditable, or unreadable through its own tools, and the command reports one count for each leaf, its human messages. Under the specs' default a revision that a human wrote under a revoked leaf is still dropped where it is delivered as a message, search included (spec 2, Open question 55).
17. **The server verifies the stored base revision before a memory edit or a task update.** (Open question 17, option A.) An unverified base answers `conflict` and names the reason. A full replacement that supplies the whole document is still accepted; this is also how content from a revoked period is written again. **Superseded by Decision 40**: the server verifies nothing it stored.
18. **The `users` list is database state; accepted.** (Open question 27, option A.) Whoever can sign in as a human is a human to every agent. The signed email is shown in the MCP receive result and in the TUI.
19. **Clients get the root, the chain and the CRLs from the discover document**, not from registration or token responses. (Open questions 1 and 2; this changes the first draft's recommendation and the outline's "at registration".) A client with no pinned root pins from discover on first contact and stores it in `<config dir>/trust/<profile>/`. A different root later is an error until `-accept-new-root`. HTTPS is required by default for a server profile; a client configuration override switch, for local testing, disables the HTTPS requirement. Registration and token responses keep their current shapes. **Extended by Decisions 23, 30 and 34** (the installation name is pinned with the root; an optional expected root; what a root renewal and a root expiry mean).
20. **The server stops a Slack message from being ingested twice.** (Open question 23; this changes the first draft's recommendation to a third option.) Before ingesting, the bridge looks for a verified stored message carrying the same signed Slack timestamp in that channel and skips the Slack message when it finds one. Clients keep no memory of Slack timestamps. Eric accepted the limit: a writer who also deletes those rows gets them ingested again, and the `stale` mark is the remaining bound. **Superseded by Decision 40**: the look for a signed Slack timestamp is removed, and the `bridge_messages` table alone keeps a Slack message from being ingested twice, as today.
21. **A task update says when it replaces the whole document.** (Open question 28, option B.) The task patch gains `replace: true` and is then the whole document: fields it does not give take creation's values, `add_blocked_by` is the whole blocked-by list, `remove_blocked_by` must be empty, the position is `before`, `after` or the end of the siblings, and the lease and the reclaimed mark are cleared. The task keeps its id. Not taken: inferring a replacement from an update that sets every field (A), and no replacement for tasks, only delete and create again with a new id (C). **Superseded by Decision 40**, with Decision 17, whose replacement path it served: the task patch gains no `replace`.

## Decisions on the security review (Eric, 2026-11-12, human-made)

The two approved specs were given a security review (2026-11-11; 2 high, 7 medium and 6 low findings; the review is a working paper and is not in the repository). Decision 22 is Eric's general ruling. Decisions 23 to 35 are his rulings on the findings; each names its finding and the option he chose, in the review's lettering. Finding 11, Finding 13 and item 5 of Finding 15 were dropped on the ground of Decision 22 and change nothing. Where a ruling needed a detail it did not give, the detail is one of plan rulings 30 to 41 below, which are not his.

22. **A database writer is effectively an administrator of the agentmesh server, and the server is not defended against its administrator.** (General ruling.) A finding whose premise is "a database writer could" is not raised. Dropped on that ground: Finding 11 (a task's channel is not checked against the signed one), Finding 13 (after a forced renewal the revoked rows no longer hold a Slack message back), Finding 15 item 5 (the counts of Decision 16 read a plain column) and the database-writer half of Finding 15 item 1.
23. **The certificates bind the installation.** (Finding 1, option A.) The intermediate's subject carries an installation name; the server has a matching setting; the client pins the name with the root; both verifiers accept only intermediates with that subject. The intermediate and leaf profiles gain an agentmesh extended key usage, so a CA certificate the root issued for another purpose is not accepted. Not taken: one root per installation as a rule nothing enforces (B); pinning the set of intermediate keys in place of the root (C). **Extended by Decisions 36 and 37** (the usage's identifier; the root tool keeps the names distinct).
24. **A human message's origin time is bounded.** (Finding 2, option B.) The verifier refuses a `slack_ts` later than `ts` plus a small leeway, and marks or refuses a `ts` ahead of the client's clock. Decision 6's bound and accepted risk 8 are restated in plain words: a leaked leaf key signs agent messages, memory revisions and task documents dated inside its window forever unless it is revoked; human messages from it are history after the stale bound. Not taken: refusing messages from an expired leaf unless first seen before the expiry (C), which contradicts Decision 5. **Partly overtaken by Decision 40**: the bound is stated in terms of the `stale` mark and of signed agent messages, memory revisions and task documents, and none of those is in the design any more; accepted risk 8 restates it. The two checks are kept in spec 2 as they stand, with a drop where this decision allowed a mark. Whether they still have a purpose is spec 2, Open question 58.
25. **Verifiers enforce a maximum leaf lifetime, and a leaf with no row can be revoked.** (Finding 3, options A and B.) Both verifiers refuse a leaf that is valid for longer than 720 hours plus 60 seconds. The host command `agentmesh server admin signing-key revoke -cert FILE | -serial S` revokes a leaf that has no row. Not taken: every process putting its own leaves back on the CRL at a forced renewal (C).
26. **An intermediate is revoked by key.** (Finding 4, option A with B.) A verifier treats an intermediate key as revoked when any certificate with that subject key identifier is on the root CRL. `ca revoke` revokes every certificate of the same key and says so, and the outside-CA guide says the same. Not taken: renewal always with a new key (C).
27. **A restore or a rollback neither undoes revocations nor strands clients.** (Finding 5, all four options.) CRL numbers are time-based; clients and the server keep a growing union of revoked serial numbers; the server sends the bundle whenever the client's trust number differs from its own; the backup guide says what a restore does to the CRLs and what to do after one. **Extended by Decision 39** (the trust number is time-based too).
28. **With spec 2, the forced-renewal API operation requires the human claim as well as the administrator flag.** (Finding 6, option A.) Agents cannot call it; an operator uses a sign-in or the host command. Not taken: removing the API operation (B); a cooldown and a confirmation value on the API form (C). **Ratified under the reduced scope by Decision 41; where the check sits is Decision 42.**
29. **A human-only read of unverified content.** (Finding 7, option A.) `-show-unverified` on the CLI reads and a toggle in the TUI, never in MCP results, labeled "unverified, do not trust". `docs/ops/upgrade.md` says that re-signing makes the operator the author of whatever the row held. Not taken: an export host command (B); accepting the loss (C). **Superseded by Decision 40**: there is no read of unverified content.
30. **An optional expected root.** (Finding 8, option A.) The profile member `root_thumbprint`, the flag `-root-thumbprint` and the variable `AGENTMESH_ROOT_THUMBPRINT`; when it is set, first contact must match it. Discover stays the source of the certificate, so Decision 19 holds. Not taken: extending accepted risk 7 and nothing else (B). **Extended by Decision 38** (an expected installation name beside it).
31. **The Slack path: wording only.** (Finding 9, option B.) Accepted risk 2 is extended to name `human_bindings`, `slack_users` and `bridges`, and Decision 1's wording is corrected for the Slack path: there the bridge's check decides "human", and it reads those rows and the identity row's kind. The signed origin gains no `slack_team` and no `slack_channel` (A not taken).
32. **Four more rules for the message verifier.** (Finding 10.) The chain has exactly three certificates; the signing certificate is CA false with the digital signature usage; the JWS algorithm matches the certificate's key type; the SHA-256 of a supplied certificate equals the header's `x5t#S256`. Each has a row in the verification matrix.
33. **A client's own trust lag does not lose messages.** (Finding 12, all three rules.) The client applies a trust bundle before it verifies that answer's messages; a discover answer without `trust` is an error for a server profile; on `unknown_certificate` or `untrusted_chain` the client fetches discover once and verifies again before it lists the entry as unverified. Since Decision 40 a human message that fails is dropped, so these three rules are what keeps a client's lag from losing an instruction.
34. **The pin stays the root certificate.** (Finding 14, option C.) Any root renewal, one with the same key included, is a new root that needs `-accept-new-root` on every client. When the root expires, bearers stop and messages keep verifying at their signed time. The sentence that said old history no longer verifies under a new root now says so only where that is accurate under certificate pinning. Not taken: pinning the root's public key, or two pinned roots during a change.
35. **Wording fixes.** (Finding 15, items 1, 2, 3, 4 and 6.) The accepted risks below gain spec 2 section 5 item 11, without the database-writer angle. The specs say why a memory replacement with no tags is not mistaken for a partial edit, that `replayed` also marks a first delivery after a rewind inside one session, and that with the file form the intermediate key is within the server process's reach; two line citations are corrected. No mechanism changes. The wording about a memory replacement and about `replayed` went with Decisions 17 and 3 (Decision 40).

## Decisions on what the review fold left open (Eric, 2026-11-12, human-made)

Folding Decisions 22 to 35 into the specs (commit `93bc9c4`) left a list of points for Eric. Decisions 36 to 39 are his answers on the four that concern spec 1. On the passages that contradicted Decision 22 he did not rule one by one: he reopened the scope of spec 2, which is Decision 40. Decision 42 is his answer on where the forced renewal's claim check sits, and Decision 41 his ratification of Decision 28 after Decision 40. The remaining points were corrections outside the three documents, a test fixture, and one that Decision 40 made moot (who may pass `-show-unverified`; he had answered that the server returns the copy only to a bearer with the human claim). Where a decision needed a detail it did not give, the detail is one of plan rulings 42 to 54 below, which are not his.

36. **The extended key usage is identified under a Private Enterprise Number.** (Open question 29, option A.) Register a Private Enterprise Number with IANA for Trojan Unicorn Ventures; the usage is `1.3.6.1.4.1.<PEN>.1.1`. The number is pending. Spec 1 does not ship until it arrives, and no placeholder value is accepted in the code in its place. Not taken: an arc the publisher already holds (B); there is none.
37. **The shipped root tool keeps installation names distinct.** `agentmesh ca sign` refuses a CSR whose installation name it has already issued to a different public key, unless an explicit flag says this is the same installation (`-same-installation`). Under an outside CA, distinct names stay the operator's duty, and the documents say so.
38. **An optional expected installation name.** A separate setting beside `root_thumbprint`: the profile member `installation`, the flag `-installation` and the variable `AGENTMESH_INSTALLATION`. When it is set, the name at first contact must match it; otherwise the client stops and pins nothing. A held pin that differs from it is an error.
39. **The trust number is time-based, like the CRL numbers.** It is the larger of the current time in Unix milliseconds and the previous number plus one, a 64-bit integer (`BIGINT` on Postgres). Eric asked whether 2038 affects it; it does not. The number still only goes up, so the append check that orders it keeps working.
40. **Spec 2 is reduced to human messages.** His reasons: once signing and key storage have left the database, the only database content he wants protected is whether a message came from a human; he does not want to spend performance signing or verifying messages that are not from a human; and for a human message the agent must know whether it is a replay of something it has already seen and whether it is relevant in its current context, most of which a timestamp and a parent message ID under the signature give. Four parts:
    1. *What is signed.* Only messages the server appends with sender kind human: the bearer carries the human claim, or the Slack bridge's human check passed. The signature binds, in full, the sender identity, the human kind, the channel, the content (subject, body, type, tags, metadata), the timestamp, `reply_to` and a unique message ID.
    2. *Replay.* A client drops a human message whose signed timestamp is earlier than the receiving session's open time; a resumed session keeps its original open time. So a message sent before a brand-new session opened is never delivered as human. Each session keeps the set of message IDs it has seen, in the session state file, and drops a repeat silently. A human-claimed message that fails verification is dropped, not downgraded.
    3. *Relevance.* The client marks each delivered human message `in_context`: true when it has no parent, or when its parent is a message this session received or sent (the same state file). Nothing is dropped for relevance.
    4. *What is removed* from spec 2 and from this ADR: the signing and verifying of non-human messages, memory revisions and task documents; Decision 17 and its `-replace` path; content that a forced renewal makes unreadable or uneditable; `-show-unverified` and the TUI toggle (Decision 29); Decision 20's de-duplication by the signed Slack timestamp; and the four passages that contradicted Decision 22 (consequence 4 as it stood, "integrity no longer rests on the database" in spec 2 section 2, Decision 17's rationale and Decision 20's premise).

    Superseded by it: Decisions 8, 14, 17, 20, 21 and 29. Changed by it: Decisions 11 and 16. Spec 1 changes only where it says what spec 2 adds. Two decisions he did not name lose their mechanism or their purpose, Decisions 3 and 24; their entries say how the specs treat them, and spec 2, Open question 58 asks him. Decisions 1, 2, 18 and 31 stand: who is a human, the signed origin and the shown email.
41. **Decision 28 stands under the reduced scope.** Eric ratified it on 2026-11-12, after Decision 40: the forced-renewal API operation requires the human claim as well as the administrator flag, although a forced renewal now costs human messages and no longer memories and tasks.
42. **The claim checks are decided in `decide`.** (The fold had put the forced renewal's human-claim check beside the administrator check in the signing key rules and flagged it, because ADR 0011 makes `internal/core/access` the one place that decides who may do what. Option A.) `access` gets the human claim as a fact, and `decide` gains two actions: the forced renewal, which requires the administrator flag and the human claim, and the read of an unverified copy, which requires the human claim. Decision 40 removed that read, so only the first action is built.

## Plan rulings Eric approved with the design sections (2026-11-11)

Each was proposed during the design session and approved by Eric as part of a design section. They are not among his numbered decisions, and he may overrule any of them. Where a later decision of his changed one, the item says so.

Names:

1. The stale setting is `human_stale_hours` and applies to every session. **Gone with Decision 3's marks** (Decision 40; spec 2, Ruling 53 and Open question 58).
2. The root tool's commands are `agentmesh ca init | sign CSR | revoke CERT`. **Extended by Decision 37**: `sign` takes `-same-installation`.

Section 1, the hierarchy:

3. The server pins the root from a file named by a setting. The client receives it in the registration response and stores it beside its credential; a different root later is an error needing re-registration. **Changed by Decision 19**: the client receives it from discover, stores it in its own directory, and replaces it only with `-accept-new-root`.
4. `agentmesh server admin ca csr` makes the intermediate key and prints the request; `ca install CERT` checks the certificate against the pinned root (CA true, path length 0, certificate and CRL signing) and stores it; `ca install-crl` stores a root CRL; `ca status` reports. **Extended by Decision 23**: the request carries the installation name, and `ca install` also checks the name and the extended key usage.
5. The intermediate certificate, the leaf certificates and the CRLs are public and self-verifying and live in one database table. Nothing is distributed to replicas by file, and a tampered row fails verification.
6. Without a valid intermediate the server exits 2 and names the two commands.
7. The leaf is Ed25519 with a validity window W, default 7 days (Eric approved the default), settable. At W/2 the process issues its next leaf and signs with it; the previous one verifies until it expires. A failed renewal is retried after one eighth of the remaining time, never sooner than a minute. With an expired, unrenewed leaf, writes and the token exchange answer a retryable 503 and reads continue. A bearer's lifetime is capped at W/2. **Narrowed by Decision 40**: the only writes that need the leaf are appends of human messages.
8. The intermediate signs a numbered leaf CRL. The rotate operation becomes: issue a new leaf here and put every other live leaf on the CRL; other replicas see their leaf listed and issue a new one at once. The root tool revokes an intermediate and emits a root CRL. **Extended by Decisions 25, 26 and 27**: a host command revokes one leaf that has no row; the root tool revokes every certificate of the intermediate's key; CRL numbers are time-based.
9. Removed: the `signing_keys` table, the in-database key provider, and the rotation and removal maintenance jobs.

Section 2, signed messages:

10. `core.Append` signs with the in-memory leaf after the transaction assigns the sequence number, and stores the blob in a new `messages.signed` column. The payload holds the sequence number, channel id, channel name at signing, sender, sender kind, session, server timestamp, type, subject, content, reply-to, metadata, memory id, revision, tags and origin. The existing columns stay as extracted copies. Storage roughly doubles and counts against the budget. **Changed by Decision 40**: `Append` signs only a message with sender kind human; the payload is that decision's list plus the session, the display name and the origin, without the memory id and the revision (spec 2 section 4.4); only a human message's storage doubles.
11. The bearer gains a kind claim; `Append` takes the sender kind from the claim or from the bridge's Slack check. (The claim exists already, `internal/auth/token/issuer.go:266-273`; what is new is carrying it to the write, and an email claim. Spec 2 section 4.5.)
12. On the wire each message carries `signed`; responses with messages carry the referenced leaf certificates; session open and receive carry the CRL number and, for a client that is behind, the CRLs and the chain. **Changed by Decision 27**: for a client whose number differs. **Narrowed by Decision 40**: only a human message carries `signed`.
13. One shared client verification package serves the CLI, both MCP servers and the TUI, on server profiles only. It checks the chain to the pinned root, the CRLs, that the signed timestamp is inside the leaf's window, and that the signed sequence number and channel id match the delivery; then it discards the unsigned copy. A delivery under a channel name different from the signed one is flagged `renamed`. **Extended by Decisions 23, 24, 25, 26 and 32**: the chain check also asks for the installation name, the extended key usage, the leaf lifetime ceiling, revocation by key and the four rules of Decision 32; the Slack origin time is checked against the signed time. **Changed by Decision 40**: it verifies human messages only and keeps nothing of the unsigned copy of one; `renamed` is a note on a verified human message and no longer means history (spec 2, Ruling 25).
14. On failure the content is withheld, the receive result lists `unverified` entries (channel, sequence number, reason), the cursor still advances, and the agent text says to report it to the operator. **Extended by Decisions 29 and 33**: a person can ask to see the unverified copy; a failure that may be the client's own lag gets one more try first. A tombstoned message has no blob and is never an instruction. (Ruling 16 below keeps the blob, because tombstoned rows keep their content today.) **Changed by Decision 40**: a human message that fails is dropped, and nobody can ask for the copy. The listing (channel, sequence number, reason) is kept under the name `dropped` as a plan ruling, for every drop but a repeat (spec 2, Ruling 49 and Open question 57).
15. The threat model states in plain words what is not covered: deletion and suppression of messages, agent status text, ACLs and the administrator flag, a rolled-back CRL.

Section 3, operations and tests:

16. Exit 2: no pinned root, no intermediate certificate, a certificate that does not chain or does not match the key, an intermediate that is expired or on the root CRL. Exit 1: the key service does not answer at start.
17. Intermediate renewal is `csr` and `install` again; earlier intermediates stay in the table, so history under an expired intermediate verifies and history under a revoked one does not. **Changed by Decision 26**: revocation is of the key, so one listed certificate revokes every certificate of that key.
18. The registration response carries the root, the chain and the CRLs (trust on first use over the registration connection); `agentmesh-mcponly register` likewise. **Changed by Decision 19**: the discover document carries them.
19. The health document's administrator tier reports the intermediate and leaf expiry, the CRL numbers and the last renewal failure, and warns from 30 days before the intermediate expires.
20. `ca install` and `ca install-crl` are idempotent; CRL updates run under a Store lock with the number raised in one transaction; a crash between issuing and using a leaf leaves an unused certificate.
21. The schema is changed in place in `0001_initial.sql`; no migration; local data is recreated (the pre-release rule).
22. Tests: fixtures build a throwaway root in process through the root tool's package; a client verification matrix; renewal and retry on a fake clock including expiry to 503; replicas on both engines; signed append in the Store and Bus conformance suites; the wire, tool coverage, bounds, example and Arazzo gates updated; a new import rule for the verification package with selftest mutations.

## Consequences

1. No private key and no trusted public key is in the database. Reading the database or a backup no longer yields a signing key, and inserting a key row no longer yields a trusted key. Threat 2 is closed for bearers once spec 1 is built.
2. Server mode needs a CA before the first start: four commands with the shipped tool (`ca init`, `ca csr`, `ca sign`, `ca install`), or the same with an outside CA. Every server test fixture, `scripts/docker-smoke.sh` and `scripts/cats-harness.sh` gain that step.
3. The intermediate key becomes the installation's most valuable secret after the root key. In file form it is a file every replica reads.
4. Whether a message came from a human is the one statement about database content that is protected (Decision 40). It is a signed statement that rests on the sign-in or the Slack check, not on an identity row, and a client drops a message that claims to be from a human and does not verify. Everything else in the database is its administrator's (Decision 22).
5. Clients do the work for human messages only: a signature check and a chain check for each, with certificates cached. A human message takes roughly twice the storage and twice the bytes in a response; other messages are unchanged (Decision 40).
6. The wire, the Store contract, the schema, the settings and the host commands change in place, with no migration and no compatibility path (the pre-release rule of 2026-10-25). The protocol version stays `1.0.0`.
7. A forced renewal is an emergency tool (Decision 16). With spec 2 it makes the human messages the revoked leaves signed undeliverable; memories and tasks stay editable, and readable through their tools (Decision 40; spec 2, Open question 55 for what search and history then show of a human's revisions). With spec 2 the API form needs a human administrator's sign-in; an administrator agent can no longer call it (Decisions 28 and 41). That rule is decided in `internal/core/access`, which learns one fact about a request, its human claim (Decision 42).
8. The verifying layer sits under the `Bus`, so `internal/tui`, `internal/mcpserver`, `internal/mcpcli` and `internal/cli` keep their import rules.
9. A client profile that points at an `http` server on another host stops working until its URL is `https` or the override switch is set (Decision 19). Today any `http` URL is accepted (`internal/profile/config.go:132-153`).
10. The discover document grows by the trust bundle, a few kilobytes, and is fetched once by every client process that opens a server profile.
11. The server never reads its own signed messages back. The two places that did are gone with Decisions 17 and 20 (Decision 40).
12. Every server has an installation name, in its configuration and in its intermediate certificate, and an outside CA's procedure has to issue the name and the extended key usage (Decision 23). The usage's identifier is `1.3.6.1.4.1.<PEN>.1.1`, and the number is pending at IANA; spec 1 cannot ship without it (Decision 36).
13. A root renewal is an action on every client, a same-key renewal included (Decision 34).
14. A client keeps one more file, the revocations it has seen, and makes one more discover call when a human message fails for want of trust (Decisions 27 and 33).
15. A session's state file records what the session has taken: its open time, the human messages it has seen, and what it received or sent. A human message from before a session opened is not delivered to it, and a human message is delivered to a session once (Decision 40).
16. A key change of one installation needs `-same-installation` at the shipped root tool (Decision 37), and a client profile can name the installation it expects as well as the root (Decision 38).

## Accepted risks, in plain words

**General ruling (Eric, 2026-11-12, human-made; Decision 22).** A database writer is effectively an administrator of the agentmesh server, and the server is not defended against its administrator. The items below are read under it. Items 2, 4, 7 and 8 were restated, and items 11 and 12 added, by his rulings of 2026-11-12 on the security review. Items 3, 4, 5, 6, 7, 8 and 10 were restated, and items 13 and 14 added, for Decisions 36 to 42 of the same day.

1. Whoever can write the database can still act as the application's administrator: set the administrator flag, add a login key for any agent and obtain a genuine agent bearer, edit ACLs, identity rows and the `users` and `admins` lists. Replicas and restores are included (Decision 15).
2. Whoever can write the database can add an email to the `users` list; the person who signs in with that email at the provider is then a human to every agent. The signature says "signed in at the provider with this email", not "is an authorized operator"; the email is shown (Decision 18). The Slack path rests on more rows (Decision 31): whoever can write the database can bind the email of any full member of the workspace in `human_bindings`, change `slack_users`, or point a `bridges` row at another Slack channel, and that member's Slack posts, or a bound human's posts in the other Slack channel, are then signed `human` on the bridged channel. The signed origin names the Slack user and the email, not the workspace or the Slack channel.
3. Whoever can write the database can delete, hide or delay messages, a human's included, and can write or change everything that is not a human message: agents' messages, memory revisions and task documents, agent status text and server notice text. None of that is signed (Decision 40).
4. Whoever can write the database can hide a revocation from clients and server processes that have not seen it (Decision 6), and can keep a leaf off the CRL by removing its row before a forced renewal (Ruling 8). The hidden leaf's expiry ends its bearers. It does not end its human messages (Decision 5): to a party that has not seen the revocation, a human message the leaf signed with a time inside its validity period keeps verifying. A client keeps every revocation it has seen (Decision 27), and a leaf with no row can be revoked once its certificate or serial number is known (Decision 25).
5. What a session takes as a human message rests on the client's clock and on the session state file (Decision 40). A client whose clock is behind takes human messages from shortly before the session opened. A human message sent after a session opened, and not yet seen by it, is delivered whenever the server hands it over. An agent's session with no state file takes no human message.
6. Whoever can write the database can delete the Slack bridge's rows and have the server ingest a Slack message again as a new human message with a new time. No client stops it: Decision 40 removed the check of Decision 20 (spec 2 section 5 item 8 and Open question 58).
7. A client pins the root and the installation name from the first discover answer it gets (Decisions 19 and 23). Over HTTPS that answer comes from whoever holds a certificate for the server's name that the system's roots accept. With the override switch on, on a network that is not loopback, anyone on the path can supply a root. A profile that names an expected root pins no other root, and one that names an expected installation pins no other installation's name (Decisions 30 and 38); without them, every start of a client that keeps no configuration directory is a first contact.
8. Whoever holds the intermediate key, or may ask the key service to sign with it, can mint bearers and sign human messages for anyone. With the file form that includes whoever can read the server process's memory or act as its OS user, because the process reads the key file (Decision 35). Whoever can read a server process's memory has its leaf key. A leaked leaf key mints bearers until the leaf expires or is revoked. In plain words, for messages (restated for Decision 40; the wording of Decision 24 spoke of the stale bound): a leaked leaf key signs human messages, for any sender and email, dated anywhere inside its window, and expiry does not end that. A session takes one when its time is not before the session's open time and its ID is new to the session, so a session opened before the leaf's "not after" stays exposed for as long as it lives. Revoking the leaf ends it.
9. A bearer signed by a leaf that was just revoked is accepted by other replicas for up to 30 seconds.
10. A forced renewal or an intermediate revocation makes every human message those certificates signed unverifiable, and clients drop them. There is no re-sign path and no way to read a dropped message; one that was not yet delivered has to be sent again (Decisions 16 and 40). Memories and tasks stay editable, and readable through their tools. Under the default of spec 2 (Open question 55) the dropped messages include the revisions that a human wrote under those certificates: they no longer appear in search, history or receive, so an agent that finds a memory by search does not find it until someone edits it again.
11. Any root renewal is a new root to every client, a renewal with the same key included: each client needs `-accept-new-root`. When the root expires, bearers stop until a new root is in place and every client has accepted it; messages signed before the expiry keep verifying (Decision 34).
12. Search ranking, embeddings and the Slack copies are made from the database columns, not from the verified payload (spec 2 section 5 item 11; Decision 35).
13. Under an outside CA nothing checks that two installations under one root have different names, and at the shipped tool `-same-installation` is the operator's word. Two installations that share a root and a name accept each other's bearers and human messages (Decisions 23 and 37).
14. The memory and task tools verify nothing, so who wrote a revision is display text there, a human included. A human's edit of a memory or a task is signed as that human's message, and the fields the edit did not give come from the stored row (spec 2 section 5 items 3 and 4; Decision 40).

## Open questions

Four, all in spec 2 (its section 12), all about how to read Decision 40. The text of spec 2 follows the recommendation in each case and says where.

- **Open question 55**: is a memory revision or a task document that a human writes signed as a human message? Recommendation: yes, by the one signing rule, and the memory and task tools verify nothing.
- **Open question 56**: where the rules apply: which reads verify, whether the TUI applies the session rules, and what a session with no state file does. Recommendation: verify on receive, history and search; no session rules for the TUI; an agent's session with no state file takes no human message.
- **Open question 57**: is a drop reported? Recommendation: every drop but a repeat, as an entry with channel, sequence number and reason.
- **Open question 58**: what is left of Decisions 3 and 24, which Decision 40 does not name, and whether the session rules should use the Slack timestamp now that Decision 20 is gone.

Settled: the first draft's Open questions 1 to 27 by Decisions 16 to 20 or as the plan rulings listed above; the second draft's Open question 28 by Decision 21 (now superseded); Open question 29, the identifier of the extended key usage, by Decision 36. ## Alternatives not taken

- Confirming key rows with the key source alone (the first proposal of 2026-11-09): it closes one of several paths a database writer has.
- A CRL pull endpoint with next-update enforcement, and failing closed on a stale CRL: Eric chose broadcast only (Decision 6).
- Verifying every message, and signing every append (Decisions 8 and 14 of 2026-11-11): on 2026-11-12 Eric reduced both to human messages (Decision 40).
- Delivering a human message that fails verification as an agent's message, or with a warning: Eric chose to drop it (Decision 40).
- Verifying a stored revision before building on it, and a human-only read of unverified content (Decisions 17, 21 and 29): removed by Decision 40.
- Signing agent statuses: left unsigned (Decision 8).
- The root, chain and CRLs in the registration and token responses (the first draft's recommendation): Eric chose the discover document (Decision 19).
- Clients remembering Slack timestamps to mark a repeat (the first draft's recommendation), or accepting repeats within the stale bound: Eric chose a check on the server (Decision 20), and removed it again with Decision 40; a repeated ingest is accepted risk 6.

- A counter for the trust number, a note in place of a refusal in `ca sign`, and no expected installation name (Rulings 34, 30 and 35 as first written): Eric chose otherwise (Decisions 39, 37 and 38).
